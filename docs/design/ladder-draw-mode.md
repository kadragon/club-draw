# 사다리 추첨 방식 (Ladder Draw Mode)

## Problem Statement

club-draw의 추첨 연출은 원판(룰렛) 하나뿐이다. 상품을 목록 순서대로 한 개씩 돌리므로 인원·상품이
많으면 무대 시간이 길어지고, 참가자가 연출에 직접 참여할 여지도 없다. 동아리 행사에서 익숙한
**사다리 타기**는 참가자가 자기 출발 위치를 고르고, 가로줄을 보태는 식으로 참여할 수 있으며, 한
장의 사다리로 여러 상품을 한꺼번에 배정한다. 룰렛은 그대로 두고 추첨 방식을 하나 더 둔다.

리서치(네이버·seq.kr·url.kr·makers.tokyo·sciencelove·Wikipedia *Ghost leg* 등)에서 확인한 사실:

- 가로줄을 무작위로 긋기만 한 사다리는 **균등하지 않다.** 6줄·가로줄 10개면 제자리 도착이 약 37%,
  반대 끝 도착이 약 1%다. 가로줄 수의 홀짝이 순열의 홀짝을 고정해 n!개 중 절반은 나오지도 않는다.
- 한국 사다리 사이트에서 가로줄을 손으로 편집하는 기능은 찾지 못했다. 이번 요청의 차별점이다.
- 흔한 기능은 결과 가림막, 이름을 클릭해 한 명씩 공개, 전체 공개, 참가자별 색 경로, 결과표다.
  가로줄 밀도 단계(makers.tokyo)와 "Crypto API 기반" 공정성 표기(seq.kr)는 도입할 가치가 있다.

## Solution

설정에 **추첨 방식(원판 / 사다리)** 을 추가한다. 원판은 코드와 동작 모두 그대로다. 사다리는 다음
순서로 동작한다.

1. **구성** — 세로줄은 미당첨자 수 N만큼 만든다. 하단 칸 N개에는 목록 앞쪽부터 남은 상품
   `min(M, N)`개를 넣고, 남는 칸은 "꽝"으로 채운다. 하단은 가림막으로 가린다.
2. **배치** — 운영자가 명단 칩을 클릭한 뒤 상단 칸을 클릭해 참가자를 배치한다. "나머지 랜덤 배치"로
   빈 칸을 한 번에 채운다.
3. **가로줄** — 밀도 3단계로 무작위 생성한 뒤, 클릭으로 추가하거나 삭제한다.
4. **시작(잠금)** — 편집을 잠그는 순간 하단 배치를 crypto 균등 셔플로 확정한다.
5. **공개** — 이름을 클릭하면 그 참가자의 경로를 한 명씩, "전체 공개"를 누르면 남은 경로를 차례로
   재생한다. 도착 칸의 가림막이 풀리는 순간 결과를 상태에 반영하고, 모두 공개되면 결과표를 띄운다.

**공정성은 사다리 모양이 아니라 하단 셔플에서 나온다.** 사다리는 어떤 모양이든 고정된 순열 σ이고,
하단 배치 π는 잠금 시점에 균등하게 뽑힌다. 배치와 가로줄 편집이 모두 π를 모른 채 끝나므로
π∘σ도 균등하다. 따라서 가로줄을 손으로 추가해도 누구에게 유리해지지 않는다. 무작위 사다리의
비균등성은 결과에 영향을 주지 않는다.

## User Stories

- 운영자로서 설정에서 추첨 방식을 사다리로 바꾸고 싶다. 인원이 많을 때 상품 여러 개를 한 번에
  배정하려고.
- 운영자로서 참가자가 원하는 출발 칸에 그 사람을 넣고 싶다. 무대에서 "몇 번 줄로 갈래요?"를
  진행하려고.
- 운영자로서 빈 칸을 한 번에 무작위로 채우고 싶다. 모두 고를 필요가 없을 때 시간을 줄이려고.
- 운영자로서 가로줄을 생성하고, 참가자 요청에 따라 한 줄씩 보태거나 지우고 싶다. 참여감을 주려고.
- 참가자로서 결과가 편집이 끝날 때까지 가려져 있기를 바란다. 미리 경로를 계산할 수 없게.
- 운영자로서 한 명씩 공개하거나 한꺼번에 공개하고 싶다. 긴장감과 진행 시간을 고를 수 있게.
- 운영자로서 사다리 결과가 룰렛 결과와 같은 기록·CSV에 남기를 바란다. 한 세션에서 두 방식을
  섞어 쓰려고.

## Implementation Decisions

- **설정 축 분리.** `Settings.method: "wheel" | "ladder"`를 새로 둔다. 기존 `DrawMode`(`all`/`preference`,
  후보 집합 규칙)와는 다른 축이다. 로드 시 알 수 없는 값은 `"wheel"`로 강등한다(`readMode`와 같은 패턴).
  선호 모드에서는 사다리 선택을 비활성화하고, 저장된 `method`가 `"ladder"`여도 원판으로 동작한다.
  상품마다 후보가 다른 선호 모드는 한 장의 사다리로 표현할 수 없다.
- **가중치 없음.** 사다리는 1인 1칸이라 `cumulativeWins` 핸디캡을 반영할 수 없다. 균등 추첨이고,
  공정성 안내에서 이를 명시한다. 가중치가 필요한 추첨은 원판을 쓴다.
- **순수 코어 `src/ladder.ts`**(DOM 없음, `draw.ts`와 같은 층). 테스트로 커버한다.
  - 모델: 세로줄 수 `n`, 높이 단계 수 `rows`, 가로줄 집합 `{row, col}`(col과 col+1을 잇는다).
  - `canPlaceRung`: 범위 안이어야 하고, 같은 row에 인접 가로줄(col−1, col+1)이 없어야 한다.
  - `toggleRung`: 있으면 지우고, 없으면 `canPlaceRung`을 통과할 때만 추가한다.
  - `generateRungs(n, rows, density, rng)`: 밀도 3단계. `canPlaceRung` 제약을 지키며 무작위로 생성한다.
  - `traceLadder(ladder, startCol) → { endCol, path }`: row 위에서 아래로 따라간다. 렌더용 꼭짓점
    목록도 함께 돌려준다.
  - `shuffleSlots(prizes, n, rng)`: 앞쪽 `min(M, N)`개 상품 + 꽝(null)을 Fisher–Yates로 섞는다.
    난수는 `draw.ts`의 `randomBelow`를 재사용한다(모듈로 편향 없음, `RandomSource` 주입).
- **결과 결정 시점.** 하단 셔플은 "시작"(편집 잠금) 순간에 한 번만 한다. 잠금 전 하단은 비어 있고
  가림막으로 덮인다. 잠금 뒤에는 배치도 가로줄도 바꿀 수 없다.
- **Golden Principle 확장.** 원판의 "결정 후 연출"과 같은 구조다. 결과는 `traceLadder` + 셔플이
  정하고, 경로 애니메이션은 그 path를 그리기만 한다. 애니메이션이 멈춘 칸 == 반영된 상품이어야 한다.
- **렌더 `src/ladder-view.ts`**(브라우저, `wheel.ts`와 같은 층). Canvas 렌더와 좌표 ↔ (row, col) hit-test,
  경로 애니메이션을 맡는다. 도메인 로직을 호출하지 않고, 이미 계산된 path만 받는다.
- **배치 UX.** 클릭 두 번 방식이다. 명단 칩을 선택한 뒤 상단 칸을 누르면 배치하고, 배치된 칸을
  다시 누르면 해제한다. 드래그는 쓰지 않는다(터치·접근성 비용). 칩과 칸은 키보드로도 조작할 수
  있는 `<button>`으로 만든다. 이름은 `textContent`로만 넣는다.
- **상태 반영.** 한 명이 공개될 때마다 당첨이면 참가자 `excluded`, 상품 `drawn`/`winnerId`를 바꾸고
  `DrawRecord`를 추가한 뒤 persist한다. 꽝이면 아무것도 바꾸지 않는다. `cumulativeWins`는 자동으로
  올리지 않는다.
- **진행 중 사다리는 저장하지 않는다.** 사다리 레이아웃은 메모리에만 둔다. 새로고침하면 공개된
  결과만 남고, 미공개 칸은 미추첨으로 돌아간다(다시 구성하면 새로 셔플한다).
- **연출.** 참가자별 경로 색은 DESIGN.md 팔레트 안에서 고른다. 재생 속도는 기존 `spinMs`에서
  파생한다. 당첨 칸에 도착하면 기존 컨페티와 사운드를 쓴다. `prefers-reduced-motion`이면 경로를
  즉시 그린다(`motion.ts` 게이트). 추첨 경로에는 네트워크 호출이 없다.
- **결과표.** 모두 공개되면 "출발 칸 · 이름 → 결과" 표를 보여 준다. 기존 결과 보기 오버레이의
  스타일을 재사용한다.
- **공정성 안내.** 공정성 모달에 사다리 항목을 추가한다(crypto 셔플, 잠금 시 확정, 가로줄 편집과
  결과 무관, 가중치 없음).

## Testing Decisions

- `test/ladder.test.ts`(vitest, `bun run test`)
  - **절대값 assert**: 손으로 계산한 소형 사다리(예: n=4에 가로줄 몇 개)의 `traceLadder` endCol과
    path 꼭짓점을 고정한다. round-trip만으로는 확인하지 않는다(순환 테스트 금지).
  - 전단사: 무작위로 생성한 사다리에서 모든 startCol의 endCol이 서로 다르다.
  - `canPlaceRung`/`toggleRung`: 인접 가로줄 거부, 범위 밖 거부, 토글 왕복.
  - `generateRungs`: 결과가 `canPlaceRung` 제약을 전부 만족하고, 밀도 단계가 올라갈수록 개수가
    단조 증가한다(주입 rng로 결정론적 확인).
  - `shuffleSlots`: M<N이면 꽝 N−M개, M>N이면 앞쪽 N개만 들어간다. 주입 rng로 순서를 절대값으로 고정한다.
    가짜 rng로 모든 순열이 나올 수 있는지도 확인한다.
  - 회귀 가드: `traceLadder`에서 가로줄 방향(col ↔ col+1)을 뒤집으면 절대값 테스트가 빨개져야 한다.
- `test/state.test.ts`: `method` 로드 시 알 수 없는 값은 `"wheel"`, 기존 페이로드(필드 없음)도 `"wheel"`.
- 브라우저 검증(`window.__cd` 시드): 한 명씩 공개와 전체 공개 모두에서 애니메이션 종료 칸 == 반영된
  상품 == 기록에 남은 상품인지 확인한다. reduced-motion과 콘솔 CSP 위반 0도 확인한다.
- `bun run lint`, `bun run test`, `bun run build` 통과.

## Further Notes

- 운영자는 잠금 전에 다시 구성하거나 새로고침해 셔플을 다시 할 수 있다. 하지만 셔플은 잠금 시점에만
  일어나므로, 잠금 전 재구성은 결과를 모르는 상태에서 하는 것이라 공정성에 영향이 없다. 잠금 후
  새로고침하면 공개된 결과는 남고 미공개 칸만 버려진다. 무대 규칙으로 안내한다(runbook).
- 세로줄 상한은 `LADDER_MAX_COLS = 30`이다(원판 팔레트 30색과 같다). 1440px 무대에서 30명일 때 좁은
  칸의 이름은 세로로 쓰고, 짧은 라벨("?", "꽝")은 가로로 둔다. 이 상태에서 읽을 수 있음을 확인했다.
  30명을 넘으면 사다리를 만들지 않고 상태 메시지로 안내한다.
- 구현 후 AGENTS.md Golden Principles에 사다리 불변식 한 줄과 `docs/architecture.md` 모듈 표를 동기화한다.
